# Agent Workflow — Echoes of the Grip v2

**For:** the person driving Claude Code on this repo, and the eight `eotg-*` subagents in `.claude/agents/`. Defines who owns what, the order work moves in, the gates that must close, and the handoff format. Every agent is instructed to read this file first.

**Why this exists:** v1 wrote 328 events, 7 governments, 28 cultures and 318 titles, and never produced a playable world, because content was built on top of a map layer that never loaded. v2 sequences work so that cannot recur, and splits *making* from *checking* so mistakes are caught by a different context than the one that made them.

## 1. The agents

| Agent | Role | Writes to | Read-only? |
|---|---|---|---|
| `eotg-architect` | Designs systems; produces `docs/specs/<system>.md` | `docs/` | script: yes |
| `eotg-cartographer` | Gate 1 owner — titles, provinces, map_data, history, dynasties, bookmarks, descriptor | `common/landed_titles/`, `common/dynasties/`, `common/bookmarks/`, `history/`, `map_data/`, `*.mod` | no |
| `eotg-scripter` | Implements specs — events, effects, triggers, decisions, governments, on_actions, traits, cultures, religions, MAA | `common/` (except the cartographer's folders), `events/` | no |
| `eotg-localizer` | All player-facing text; BOM; glossary; `replace/` one-definition rule | `localization/` | no |
| `eotg-qa` | Tiger runs + triage, hygiene audits, reachability, diff review | nothing | **yes** |
| `eotg-lore-keeper` | Canon authority; reviews for contradiction; supplies names | nothing | **yes** |
| `eotg-vanilla-scout` | "How does vanilla do X" lookups with paths + excerpts | nothing | **yes** |
| `eotg-intake` | Reads the lore briefs for a region, checks completeness, writes the build order in `docs/specs/regions/`, sends questions back to the vault | `docs/specs/regions/`, `intake/regions/*/QUESTIONS.md` | script: yes |

Ownership is exclusive. If an agent needs a change in a folder it does not own, it puts the request in its handoff block; it does not reach across.

The **orchestrator** is the top-level Claude Code session (the one you talk to). It dispatches agents, relays handoffs, keeps §6 (the gate board) current, and is the only thing that commits.

### Invoking
- Ask the main session: *"use eotg-qa to run a pass on the last change"*, or *"have eotg-architect spec the Corporation government"*.
- Agents run cold. Each one re-reads `CLAUDE.md`, this file, and the catalog. Keep tasks bounded (one system, one gate item, one audit) so that cold start is cheap.
- Use `SendMessage` to continue an agent that already has context rather than spawning a fresh one for a follow-up on the same task.
- Independent agents can run in parallel (e.g. lore-keeper reviewing a spec while vanilla-scout looks up syntax). Anything that writes to the same folder runs serially.

## 2. Gates (in order — no skipping)

Gate numbering follows v1's `closed_alpha_checklist.md`. A gate closes only when `eotg-qa` returns PASS on its Definition of Done **and** any in-game items are confirmed by a human.

### Gate 0 — Skeleton
- Root has `CLAUDE.md`, `docs/agent_workflow.md`, `.claude/agents/`, `descriptor.mod`, `echoes_of_the_grip.mod`, `.gitignore`.
- **Decision recorded 2026-09-21: the mod ships its own `map_data/`.** The human supplies the map image files; province ids come from the mod's own `definition.csv`, not vanilla's. Consequences: `history/provinces/` must be complete for every land province; `replace_path` for `history/provinces` and `common/landed_titles` becomes correct once those folders are populated (and only then); vanilla regions/struggle regions/holy sites do not exist and must be redefined.
- **World data is described in `intake/`** (see §3 Pipeline E and `intake/README.md`): Markdown briefs per region, written from the Obsidian vault by an external exporter. Builders read the briefs and author the script; the briefs are reference, not input to a program.
- DoD: Tiger runs against the root and produces output.

### Gate 1 — A world that loads
Owner: `eotg-cartographer`. Everything else is blocked on this.

**Map files (human-supplied, cartographer verifies presence and consistency):**
`map_data/provinces.png`, `definition.csv`, `default.map`, `heightmap.png` (+ `heightmap.heightmap` / packed variants generated by the game's map editor), `rivers.png`, `positions.txt`, `adjacencies.csv`, `climate.txt`, `island_region.txt`, `seasons.txt`, `geographical_regions/`. Any missing file is a Gate 1 blocker; cartographer lists them, does not fabricate them.

**Built from the region briefs (cartographer authors, following the build order in `docs/specs/regions/<region>.md`):**
- `common/landed_titles/` from the polity title briefs: tier-first keys, every barony `province =`, every title `color`, every county+ `capital`.
- `history/titles/` from the holder tables in the title briefs: holders and `government =` on every title that should run mod content.
- `history/provinces/` from the region map footprint + title briefs: culture, religion, holding for every land province.
- `history/characters/` + `common/dynasties/` from ruler and dynasty briefs; culture/faith key syntax verified by vanilla-scout once and recorded in `docs/specs/history_syntax.md`.
- `common/bookmarks/` from the rulers marked as bookmark leads (target 9).
- Cultures + religions from the culture / religion briefs (via scripter) — characters cannot load without them. Where no brief exists yet, v1 definitions may be lifted as a stopgap, marked `# STOPGAP: replace from briefs` so QA can find them.
- `descriptor.mod`: `replace_path` only for folders populated in the same commit.
- DoD: every barony province id exists in `definition.csv`; Tiger shows 0 `expected title` / `unknown province` / `unknown character` errors; **human confirms**: game reaches the 866 bookmark, characters selectable, map renders with mod titles.

### Gate 2 — Governments are alive
Owner: `eotg-scripter`, specs from `eotg-architect`.
- Per government: `government_rules` per the robustness plan §2; role-ladder triggers at all 4 tiers; signature resource; on_action wiring; decisions.
- DoD: each `eotg_*` government appears in `history/titles/`; QA audit 9 passes; a human plays 5 years as one ruler of each government and sees at least one government event.

### Gate 3 — Systems
Owner: `eotg-scripter`. Lift-as-is per catalog §5 (augmentation, void, legacies, MAA, struggle + regions, exodus), each audited for title-key refs and resource coupling. New systems need a spec first.
- DoD: 100% event reachability; 0 self-cancelling events; every flavor event couples to its resource (QA audit 8).

### Gate 4 — Presentation
Owners: `eotg-localizer`, human for art.
- All loc keys defined, BOM-clean, no `[scope:`; `replace/` lifted and rekeyed; name lists; CoAs; icons budgeted (art is human/external — QA reports it as debt, not error).
- DoD: Tiger clean except known-benign; no missing-loc in-game on a 10-year test.

## 3. Pipelines

### A. New system
```
human → architect (spec) → lore-keeper (canon review of spec)
      → scripter (script) → localizer (loc) → qa (PASS) → human commits
```
Scripter may call vanilla-scout at any point. If QA FAILs, it routes each finding to an owner; the orchestrator re-dispatches only those owners.

### B. Lift from v1 (catalog §5, left column)
```
human → scripter: "lift <system> from OLD PROJECT VERSION"
      → scripter copies, then audits: prefix, tier-first title refs, resource coupling, cooldown authority
      → localizer copies matching loc, rekeys, BOM-checks → qa → commit
```
No architect pass needed unless the scripter finds the system violates a §4 lesson from the catalog, in which case it stops and requests one.

### C. Gate 1 work
```
human (map_data files) + build order for the region (Pipeline E)
      → cartographer ⇄ vanilla-scout ⇄ lore-keeper (names)
      → localizer (title loc) → qa → human in-game check → commit
```

### D. Bounded fix
```
human or qa finding → owning agent → qa → commit
```

### E. Lore intake (world data from the Obsidian vault)
```
Gemini exporter writes briefs from intake/templates/ → intake/regions/<region>/ (+ intake/setting/)
      → eotg-intake reads them, writes docs/specs/regions/<region>.md (build order) + QUESTIONS.md
      → eotg-cartographer (titles, provinces, characters, dynasties, bookmarks)
        eotg-scripter    (religion families, religions, faiths, holy sites, cultures, name lists)
      → eotg-localizer (names, adjectives, descriptions, god vocabulary)
      → eotg-lore-keeper (result vs briefs vs canon)  → eotg-qa → commit
```
Rules specific to this pipeline:
- Briefs are prose for agents and people to read, not data for a program. Builders exercise judgement (which CK3 trait fits "grasping", how many provinces a "sprawling belt" gets) and record the judgement in a comment beside the script so the lore-keeper can challenge it.
- The build order is the work list; builders take items from it in order and do not build what it lists as **Blocked**.
- A fact the briefs do not settle goes into `QUESTIONS.md` for the vault, not into the script as a guess. Stopgaps are allowed only when Gate 1 cannot close without them, and are marked `# STOPGAP` on the line.
- Nobody edits the briefs on this side. Corrections go back through the human to the vault and are re-exported.

## 4. Handoff block

Every agent ends its report with exactly this, so the orchestrator can dispatch without re-reading the whole report:

```
### HANDOFF
- status: done | blocked | partial
- next: eotg-<agent> | human | none
- ask: <one sentence — what the next agent must do>
- files: <paths touched, or "none">
- needs-loc: <keys, or "none">
- needs-lore: <question, or "none">
- needs-human: <in-game check / decision, or "none">
```

## 5. Rules that bind every agent

1. `eotg_` prefix on everything. **Except** landed titles, which are tier-first: `e_eotg_`, `k_eotg_`, `d_eotg_`, `c_eotg_`, `b_eotg_`.
2. Nothing in Gates 2–4 is built while Gate 1 is open, except lift-as-is copies that are needed *for* Gate 1 (cultures, religions), and **mod-exclusive systems** built against the temporary map (decided 2026-10-02; cybernetics first). Those must not reference specific titles, provinces, characters, cultures or faiths; anything that would is recorded as a deferral for after the real map lands.
3. Additive on_action extension only. Cooldown authority in the on_action, never duplicated in the event trigger.
4. Every flavor event couples to its system's signature resource.
5. Never `replace_path` a folder you do not ship in the same commit.
6. Loc: UTF-8 BOM, bare `[x.GetName]`, one definition per key.
7. Tiger's ~74 religion/culture-folder findings are Tiger 1.17 vs CK3 1.19 — benign. Do not "fix" them.
8. Nikios Khanate content is deferred by the owner. Do not build it.
9. Makers do not sign off their own work; checkers do not fix.
10. The old tree is reference, not a working copy: read from `OLD PROJECT VERSION/`, write only to the root layout.
11. World data (religions, cultures, name lists, dynasties, characters, titles, provinces, bookmarks) is built from the briefs in `intake/` via the build order in `docs/specs/regions/`. When script and brief disagree, the brief wins until the vault says otherwise.
